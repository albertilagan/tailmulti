Tailmulti implements an independent product around selected Tailmix code. It did not implement everything from scratch, and subnet routing is deliberately unfinished. I recommend adding narrowly scoped subnet support after the existing two-tailnet direct-host acceptance milestone.

This is source research only. No builds, tests, account inspection, app operations, or host networking changes were performed. The handoff reports successful service health checks but explicitly leaves simultaneous Safari/SSH access unverified; this note does not establish live connectivity. [HANDOFF.md:7](../HANDOFF.md#L7)

Tailmulti's provenance is explicit. Seven package groups were adapted from Tailmix: `effectiveip`, `packetmap`, `tunmux`, `hosttun`, `tsnet`, `netns`, and `profile`. They provide address allocation, packet translation/multiplexing, host-interface operations, and embedded Tailscale integration. The imported code also has Tailmulti-specific packet validation, source/destination isolation, queue handling, startup preferences, and lifecycle fixes. Authentication, cryptography, and transport remain Tailscale's. The upstream daemon, CLI, control API, DNS/policy packages, installer, updater, and release automation were excluded. [ADAPTATIONS.md:3–27](../engine/ADAPTATIONS.md#L3) The pinned upstream revision is https://github.com/maisem/tailmix/commit/98d62fed39d388b8eb47b77fcb190a165e08a075.

New implementation includes persistent peer-address policy in `internal/routing`, authoritative DNS in `internal/names`, lifecycle/state publication in `internal/daemon`, authenticated control in `internal/control`, Darwin activation/recovery handling in `internal/host`, and the native SwiftUI app/menu bar. The app uses its own daemon's Unix socket and verifies its UID; it does not invoke an installed Tailmix binary. These are substantial product changes, but they do not reproduce all upstream features. [routing:110](../engine/internal/routing/plan.go#L110), [names:1](../engine/internal/names/dns.go#L1), [daemon:183](../engine/internal/daemon/manager.go#L183), [control:160](../engine/internal/control/server.go#L160), [host:200](../engine/internal/host/host_darwin.go#L200), [Swift model:33](../macos/Sources/Tailmulti/TailmultiApp.swift#L33), [Swift transport:88](../macos/Sources/TailmultiKit/ControlClient.swift#L88).

The subnet foundations already exist:

- `packetmap.Table` contains `ExactRoutes` and `ImportedRoutes`. Outbound subnet packets preserve their destination and translate the source to the selected account's address. Inbound packets must target that account's own address, and their source route must belong to that account. [packetmap:32–178](../engine/packetmap/packetmap.go#L32)
- `profile` exposes `AvailableRoutes`, derived from peers' `PrimaryRoutes`, split/default `DNSRoutes`, and `SetRouteAll`. Startup explicitly sets `RouteAll=false`. These APIs are capabilities, not enabled product behavior. [profile:228](../engine/profile/tsnetengine.go#L228), [DNS:260](../engine/profile/tsnetengine.go#L260), [SetRouteAll:373](../engine/profile/tsnetengine.go#L373), [startup:721](../engine/tsnet/tsnet.go#L721)
- Tailmulti's planner never populates those subnet tables. It installs synthetic destination host routes and emits the advertised-subnets warning. The later automatic DNS implementation forwards ordinary DNS to the physical network's resolvers; it still does not forward private DNS through an account. [Planner](../engine/internal/routing/plan.go), [DNS](../engine/internal/names/dns.go)

Tailmix supplies useful reference policy. `BuildIP` supports explicit account/prefix bindings, per-account accept-all, unavailable bindings, and inactive entries for identical prefixes imported from multiple accounts. Explicit bindings override imported routes. This is not blanket rejection of every partially overlapping prefix. Its reserved-range check covers Tailscale/synthetic ranges and local NAT addresses, not a complete live-LAN inventory. `BuildDNS` similarly supports bindings, accept-all, ambiguous domains, and automatic MagicDNS claims. Its forwarder sends requests through a selected profile dialer or profile DNS query API. [IP policy:54–177](../upstream/tailmix/routingpolicy/policy.go#L54), [reserved ranges:458](../upstream/tailmix/routingpolicy/policy.go#L458), [DNS policy:180–315](../upstream/tailmix/routingpolicy/policy.go#L180), [forwarder:38–74](../upstream/tailmix/dns/forwarder.go#L38).

My recommended first scope is explicit per-account selection of existing approved, non-overlapping subnets. Persist bindings, expose availability/conflicts in IPC/UI, enable engine route acceptance only where needed, populate packet tables, and install selected host routes. Reject default routes, reserved ranges, overlaps between accounts, and conflicts with current LAN/other VPN routes, including after network changes. Do not silently import everything. Existing advertised routes still need remote approval and access policy; client support cannot bypass those requirements. With an existing normally configured subnet router, destination machines need no Tailmulti installation. [Tailscale subnet routers](https://tailscale.com/docs/features/subnet-routers)

DNS forwarding needs separate explicit suffix-to-account policy. Send private queries through that account, preserve TCP fallback, and refuse ambiguous/unavailable suffixes without trying another account or public DNS. Private DNS servers may themselves require subnet reachability; ordinary MagicDNS cannot hold arbitrary subnet-host records. [Tailscale DNS](https://tailscale.com/docs/reference/dns-in-tailscale)

For later overlapping-subnet support, a uniquely account-selected hostname could resolve to a persistent synthetic address mapped to that account's real destination. This requires extending leases beyond known Tailscale peers and preserving reverse translation. Identical full hostnames and identical raw IPs carry no account selector: require an explicit binding/alias or refuse them. A global raw-IP lookup cannot choose both simultaneously. These are design deductions from the current name ownership and account-scoped mapping model. [plan:134–205](../engine/internal/routing/plan.go#L134), [packetmap:95–178](../engine/packetmap/packetmap.go#L95)

Return-path isolation and failure recovery are the hard parts. Retain account identity in every mapping; never bridge accounts. Withdraw forwarding on disconnect or route loss while retaining destination-specific reject protection, so packets cannot escape through LAN/default routes. Current guards protect only synthetic pools. Raw subnet guards need their own ownership/recovery design, including crash, reboot, changed LANs, and deliberate release. [host:186](../engine/internal/host/host_darwin.go#L186), [plan:223](../engine/internal/routing/plan.go#L223) Tailscale likewise retains unreachable routes on key expiry to avoid leaks. Router SNAT is normally enabled; disabling it requires a remote return route. [Subnet-router failure and SNAT behavior](https://tailscale.com/docs/features/subnet-routers)

Tailscale 4via6 distinguishes overlapping IPv4 sites using site-specific IPv6 destinations, but routers must advertise the translated IPv6 prefixes. That requires router-side configuration and approval, outside a default promising no server-side changes. Consider it optional interoperability, not the default collision solution. [Official 4via6 documentation](https://tailscale.com/docs/features/subnet-routers/4via6-subnets)

The minimal feature is moderate engineering work; reliable DNS, overlaps, and recovery make the full feature high complexity. Biggest unknowns are embedded-engine route acceptance/failover, macOS route/source selection and crash protection, DNS caching/answer translation, and packet limits such as fragments and ICMP errors. First prove two-account direct-host access and disconnect isolation. Then implement non-overlapping subnets with failure tests and controlled live acceptance, add account-specific DNS, and address overlaps last. Existing source and simulated coverage cannot substitute for those live checks.
